Schematic · deployment guide

Deploy, self-host, and lock down

1Prerequisites

  • Bun v1.2+ or Node.js v22+ (package.json scripts run under Bun).
  • A Cloudflare account with an active zone for your domain (required for Custom Domains and Access).
  • Zero Trust enabled on the account (only for the optional Access stage).
  • Repo cloned with dependencies installed. Run each line separately:
Run:
bun install
Run:
cp .env.example .env
Never commit secrets or real email addresses. Secrets go in wrangler secret put or .env (git-ignored); Access rules live only in the Cloudflare dashboard or API.

2Deploy to Cloudflare Workers

2.1 Log in to Wrangler

Run — opens a browser for OAuth:
bunx wrangler login
Run — confirm it shows your account:
bunx wrangler whoami

Wrangler is a devDependency, so bunx wrangler … is the repo's convention.

2.2 Create the D1 databases

Why create databases first instead of relying solely on the config file? The configuration file only references databases — each entry pairs a binding name (the variable your Worker code reads at env.<BINDING>) with a database_id. The database itself has to exist first in your Cloudflare account to generate that ID. The flow is: create the database → paste the returned ID into your local config.

The repository provides wrangler.sample.jsonc containing placeholder IDs. Copy it to wrangler.jsonc (which is git-ignored to keep your account's database IDs private):

Run — create local config from sample:
cp wrangler.sample.jsonc wrangler.jsonc

Schematic uses two D1 databases: transit-status-db (binding: DB_TRANSIT) for all agency routes, stops, and shape topology, and push-notifications-db (binding: DB_NOTIFICATIONS) for user push subscriptions and alert delivery history. Run both create commands, then copy each returned database_id into the matching entry in wrangler.jsonc:

Run — copy the returned ID into DB_NOTIFICATIONS:
bunx wrangler d1 create push-notifications-db
Run — copy the returned ID into DB_TRANSIT:
bunx wrangler d1 create transit-status-db
Run — confirm every database exists and the IDs match wrangler.jsonc: 
bunx wrangler d1 list

Binding names must stay valid JS identifiers. No migration files are needed: tables are created in code on first access (CREATE TABLE IF NOT EXISTS). With no D1 binding on Workers (or no DATA_DIR when self-hosting) the server fails loudly instead of silently using memory.

2.3 Set production secrets (VAPID & agency API keys)

Secrets are stored securely in Cloudflare Workers and never committed to version control. Each bunx wrangler secret put <NAME> prompts interactively for the secret value and deploys it immediately to your Worker environment. Run each secret command individually:

1. Web Push notifications (VAPID keys):

Required for desktop and mobile push notifications on service delays. Without these keys, the app functions normally, but push UI hides and background notification cycles skip:

Run — prints a public + private keypair; keep it private:
bunx web-push generate-vapid-keys
Run alone — paste the public key when prompted: 
bunx wrangler secret put VAPID_PUBLIC_KEY
Run alone — paste the private key when prompted: 
bunx wrangler secret put VAPID_PRIVATE_KEY
Run alone — optional, defaults to mailto:admin@example.com: 
bunx wrangler secret put VAPID_SUBJECT

2. Agency API keys & feed secrets:

Some transit providers require an API key or authentication token to access their real-time GTFS-RT or alert feeds. Every agency manifest (in src/agencies/<country>/<region>/<agency>/manifest.json) declares the secrets it requires under auth.secretName.

To store an API key for any agency requiring authentication, use the generic command pattern:

Generic pattern — paste the agency API key when prompted: 
bunx wrangler secret put <AGENCY_SECRET_NAME>

Supported agencies requiring an API key:

  • GO Transit (Metrolinx): Realtime GTFS-RT alerts require an API key stored under FEED_METROLINX_API_KEY. Register for a free developer key at api.openmetrolinx.com and push it to your Worker:
    Run alone — paste your Metrolinx API key when prompted: 
    bunx wrangler secret put FEED_METROLINX_API_KEY

If an optional agency secret is omitted, that agency's authenticated feeds fail gracefully with an honest diagnostic log while all other agencies continue operating normally.

For local dev, add the same keys to .env (e.g. FEED_METROLINX_API_KEY=your_key_here). To audit all active secrets on your Worker, run:

Run — verify all active secrets on your Worker:
bunx wrangler secret list

2.4 Ship only the agencies you need

If you serve one city, leave the rest out. Open src/agencies/agencyCatalog.ts and delete both import lines and the agencyCatalog entry for each agency you do not want. Keep the entries you want. Registries, seed configs, and the scheduler read this file, so they shrink to match.

Rebuild Workers from the trimmed catalog:

Run:
bun run deploy

The prebuilt GHCR image ships all registered agencies, so Docker users must build from source after the trim:

Run:
docker build -t ghcr.io/joncrangle/schematic:latest .

Seed follows the trimmed catalog, so seed all to seed only what remains:

Run:
bun scripts/seed.ts --agency=all --db=remote

The bundler skips leftover folders under src/agencies/ca/on/<id>/, so you can keep them. bun run test still complains about them, and deploy forks can ignore that warning. The app skips removed interchange hubs at runtime with no crash.

2.5 Seed the remote D1 database

Before deploying the Worker, populate static transit topology (routes, stops, shapes) into your remote Cloudflare D1 database. The seeder downloads declared official GTFS feeds for all registered seedable agencies, seeds the local SQLite projection, and reconciles it into your remote DB_TRANSIT binding:

Run — ingest all agencies into remote Cloudflare D1:
bun scripts/seed.ts --agency=all --db=remote

You can also seed an individual agency by specifying --agency=ttc, --agency=go, --agency=yrt, or --agency=kingston.

The D1 free tier includes 100,000 rows written per calendar day with a UTC reset. Initial population writes the complete selected topology. Later seeds and runtime refreshes upsert only new or changed rows and delete only removed keys, scoped by agency_id. Monitor actual rows written.

Manual SQLite seeding, self-hosted refresh, and the external remote job share a streaming GTFS projection. Automatic refresh uses archive/configuration and normalized table hashes to skip parsing and unchanged-table reads. Local and remote D1 seed targets reconcile the SQLite projection. Manual seeds verify actual destination rows despite matching hashes, so they can repair corruption without rewriting unchanged rows. Effectively unchanged topology writes zero rows, including no freshness or hash update. If only one existing stop's coordinates change, the delta is that stop plus two metadata rows, seed_topology_meta and topology_meta.

Manual seeding remains the authority for initial population and the emergency path for changes or repairs that cannot wait for the weekly refresh opportunity. An empty refresh store logs needs-seed without download, schema provisioning, or population. Review generated station-index and interchange changes from manual seeding before committing and deploying.

2.6 Build and deploy

Run:
bun run deploy

This runs bun run deploy:check && bun run build && bun run check:worker-functions && wrangler deploy — the readiness check ensures no placeholder D1 IDs remain in wrangler.jsonc before anything uploads. After the configured build, check:worker-functions sends a local RPC probe to confirm that the built Worker recognizes a client-advertised server function. The worker is named schematic, so it first goes live at https://schematic.<your-subdomain>.workers.dev. Expect the deploy output to list both D1 bindings and the minute fast-alert and fifteen-minute slow-alert crons. Workers do not execute GTFS refresh.

Cron changes can take up to 15 minutes to propagate. If you change the shell precache list in src/sw.ts, bump CACHE_NAME (currently app-shell-v1) or users may keep the old shell.

2.7 Attach your custom domain

Recommended: dashboard (Option A). Your hostname is operator-specific — committing it under routes would publish your domain and break every other deployer's deploy (their account doesn't own your zone, so the Custom Domain creation fails). Keep routes out of the repo:

A — Dashboard (recommended): Workers & Pages → schematic → Settings → Domains & Routes → Add → Custom Domain → enter your hostname. Cloudflare creates the DNS record and certificate.

B — Config file (local-only change, don't commit): add to wrangler.jsonc, deploy, then revert — useful if you want the domain creation in the deploy itself:

Add to wrangler.jsonc, then run bun run deploy: 
"routes": [
  { "pattern": "ttc.example.com", "custom_domain": true }
]

The hostname must not already have a CNAME record, and matching is exact — www. needs its own rule if you want it.

2.8 Keep alerts on Workers, schedule topology externally

* * * * * polls JSON and GTFS-RT alert sources every minute; */15 * * * * polls web and RSS sources every fifteen minutes. Both evaluate complete snapshots and send Web Push to matching subscriptions. Manage these expressions in wrangler.jsonc. Workers Free's 10 ms CPU budget cannot run GTFS projection; do not add a topology cron there.

Alert observations remain transient in the Workers Cache API; no alert-feed database or D1 writes are introduced. Mixed agencies reuse opposite-cadence observations for up to fifteen minutes (web/RSS) or 45 seconds (JSON/GTFS-RT). A cache miss fetches the source immediately, including outside its normal cadence, so eviction or a different cache location cannot fabricate an empty complete snapshot. Failed or capped crawls remain stale and suppress recovery notifications.

Each Workers cycle shares a ceiling of 49 operations across cache lookups and mutations, HTTP requests, redirects, and pushes. The current registry's uncapped cold polling alone estimates 54 operations on the fast cadence and 3 on the slow cadence, before redirects or pushes. Workers skip agencies without interested subscriptions or outstanding deliveries. Exhausted work is deferred; agency starting positions rotate each cycle, and recipient positions advance each full provider revolution to avoid correlated starvation. A separate 50-statement D1 guard includes schema and batch statements and reserves delivery or pruning writes before accepting a push. These guards bound operation counts; CPU and daily quotas still require production observation. Self-hosted polling retains its existing retry and crawl limits.

Run the portable Bun CLI from a separate cron host or Forgejo runner instead. It refreshes existing remote D1 topology directly, without a SQLite source, generated artifacts, or a Worker deploy:

Run from a checkout with credentials supplied by your job's secret store: 
bun scripts/refresh-topology.ts --config=/path/to/wrangler.json

Schedule it daily at 04:00 UTC, 0 4 * * *. The shared policy selects only seed agencies assigned to that weekday and skips fresh topology under the existing seven-day TTL. Assignments are deterministic for the registered set and can rebalance when agencies change. A failed agency does not stop the others; the CLI exits nonzero and the next scheduled retry is its next weekly opportunity. TTC NextBus crawling and alert evaluation are unchanged; request reads remain write-free.

Follow portable refresh setup for the private minimal D1 config, D1-write token, account ID, and scheduler concurrency. The included Forgejo workflow uses a configurable runner label, daily schedule, and manual dispatch only. Its official Bun setup action is fetched from GitHub but executes on the Forgejo runner, consuming no GitHub Actions minutes. It has no push, pull-request, or deploy trigger. Any other Bun-capable cron host can run the same CLI; Forgejo is not an application dependency.

An unchanged check does not advance topology_meta.last_sync, so an agency can remain due for its next weekly check. Automatic refresh never regenerates the compiled stationIndex or regional interchanges. Moved-stop warnings include before/after coordinates and direct you to run these commands in your repository checkout:

Replace <id> with the agency ID from the warning:
bun scripts/seed.ts --agency=<id> --db=sqlite
Regenerate interchanges from existing SQLite data:
bun scripts/seed.ts --interchange-only

Review and commit the generated artifacts, then deploy them. Database refresh alone does not update the deployed station index.

Smoke-test locally with vite dev running (default port 3000; 8787 is only the wrangler dev default):

Run with vite dev running — minute tick:
curl "http://localhost:3000/cdn-cgi/handler/scheduled?cron=*+*+*+*+*"

In production, check Workers & Pages → schematic → Settings → Trigger Events → View events.

2.9 Serve the public read paths from the edge cache

Three read paths are safe to share and served from Cloudflare's edge cache: /api/snapshot/:agencyId, /api/departures/:agencyId/:stationId, and /api/routes-catalog/:agencyId. Everything else stays uncached. The flag ships in wrangler.sample.jsonc (needs Wrangler 4.69+, repo pins 4.131.1; keep compatibility_date at 2025-09-02):

Already in your config copied from the sample — confirm it is there: 
"cache": {
  "enabled": true
}

Edge policy per path (browsers always revalidate; the numbers below are edge-only): snapshots stay fresh 15 seconds with 15 seconds of background refresh and 60 seconds of stale cover on origin error; departures stay fresh 20 seconds and never serve old countdowns — an expired entry waits for origin, an origin error reaches the client as an error; the routes catalog stays fresh 1 hour with 24-hour refresh and error windows. Each deploy starts with an empty cache, so the first requests after a deploy are misses while it fills.

Before enabling the cache, record Workers request count, CPU time (watch exceededCpu), and 5xx rate in Workers & Pages → schematic → Observability; record daily D1 rows read/written too. On Free, enable the available D1-limit emails and weekly Workers/CPU summaries.

After deploy, repeat the measurements and compare them with the baseline. For a cache smoke check, request a public read path twice and confirm the second response reports cf-cache-status: HIT with an age value.

Rollback (emergency only). Purge is never part of a deploy, and the zone dashboard purge cannot reach these entries — do not bother with it. To roll back: remove the §4.4 Bypass so Access covers everything again, set "enabled": false in the cache block of wrangler.jsonc, and run bun run deploy. Disabling stops the edge from reading or filling the cache on later requests.

2.10 Guard against runaway costs

Workers Paid has no spending cap: usage beyond the included allowance is billed as overage. In the dashboard, open Notifications → Add → Usage Based Billing and set a threshold so you hear about unexpected usage early. It warns but never stops the Worker.

Static assets and edge-cache hits never reach the Worker. Every other request is billed, so the app bounds it in code, and the sample config declares the settings it relies on:

  • ratelimits — the REQUEST_RATE_LIMITER binding admits 600 requests per client network (IPv4 address or IPv6 /64) per 60 seconds and answers the rest with 429. The Worker refuses to serve without this binding. namespace_id is any integer unique within your account.
  • limits.cpu_ms — 5000 ms per invocation, well above the heaviest alert cron and far below the 30-second default, so a runaway invocation fails fast. CPU limits apply on Workers Paid.
  • observability.logs.invocation_logs: false — drops the automatic per-request log line, the only log volume that grows with traffic. Application logs keep a head_sampling_rate of 1 so incidents remain diagnosable.

Each request may also issue at most 100 transit-database queries; an unknown station id returns a 404 the edge holds for 60 seconds without touching feeds or D1.

Custom domain? Set "workers_dev": false once §2.7 is done. The *.workers.dev hostname skips zone WAF and rate-limiting rules, so leaving it on gives anyone a second, unfiltered way in. Keep it true only while workers.dev is how you serve the app.

Stage check

  • whoami shows the right account; d1 list matches wrangler.jsonc; wrangler secret list confirms active secrets.
  • Remote transit-status-db is seeded with transit data.
  • bun run build emits public/sw.js + dist/.
  • Deploy lists both D1 bindings and both alert crons, * * * * * and */15 * * * *.
  • A separate topology job has private D1 configuration, credentials, and single-cycle concurrency; a manual run succeeds before relying on its schedule.
  • Custom domain serves the map; service worker registers.
  • Cron Events show minute ticks within ~15 min; a test push arrives during a severe disruption.

3Self-host with Docker or Podman (optional)

Skip this if you only want Cloudflare. Pre-built multi-architecture container images (linux/amd64 and linux/arm64) are published to GitHub Container Registry (GHCR) on every release. Pick your runtime — every command below follows the tab:

3.1 Obtain the image

Option A — Pull pre-built image (recommended):

Run:
docker pull ghcr.io/joncrangle/schematic:latest
Run:
podman pull ghcr.io/joncrangle/schematic:latest

Option B — Build from source:

Run:
docker build -t ghcr.io/joncrangle/schematic:latest .
Run:
podman build -t ghcr.io/joncrangle/schematic:latest .

The container installs locked dependencies and builds application assets and the initialization CLI. Image builds do not download GTFS feeds or seed databases. The runner uses the non-root bun user on port 3000.

3.2 Run

Podman rootless only: one-time host setup as admin, then verify:

Run (admin):
sudo usermod --add-subuids 100000-165535 --add-subgids 100000-165535 $USER
Run — confirm the ranges exist:
grep $USER /etc/subuid /etc/subgid

Create a persistent data directory, then initialize the agencies you want to serve:

Run:
mkdir -p ./data
Run once for a new data volume:
docker run --rm -v ./data:/app/data ghcr.io/joncrangle/schematic:latest init --agency=ttc,go
Run once for a new data volume:
podman run --rm -v ./data:/app/data --userns=keep-id ghcr.io/joncrangle/schematic:latest init --agency=ttc,go

Replace ttc,go with your agency IDs. Use --agency=all for every registered seed agency, or --scope=ca/on for a region. Initialization writes only SQLite and feed caches under DATA_DIR; it does not rewrite source manifests, station indexes, interchanges, or deployed lookup assets. If any selected agency is unavailable, initialization exits nonzero and reports it; successfully initialized agencies remain usable. Retry the affected agencies when their feeds recover.

Start the application after initialization:

Run:
docker run -d --name schematic -p 3000:3000 -v ./data:/app/data ghcr.io/joncrangle/schematic:latest
Run (note --userns=keep-id):
podman run -d --name schematic -p 3000:3000 -v ./data:/app/data --userns=keep-id ghcr.io/joncrangle/schematic:latest
Run — expect OK:
curl -fsS http://localhost:3000 >/dev/null && echo OK

If initialization or the server can't write to the mounted ./data (UID mismatch on the non-root bun user), re-run with --user $(id -u):$(id -g).

If initialization or the server can't write to the mounted ./data, make sure you passed --userns=keep-id as above.

Or with compose — compose.yaml automatically pulls the pre-built GHCR image, or builds locally if --build is provided. Each its own step:

Note: Podman needs a compose provider such as podman-compose installed; Docker ships docker compose built in.

Initialize once, then start:
docker compose -f compose.yaml run --rm schematic init --agency=ttc,go
HOST_PORT=3000 docker compose -f compose.yaml up -d
Initialize once, then start:
podman compose -f compose.yaml run --rm schematic init --agency=ttc,go
HOST_PORT=3000 podman compose -f compose.yaml up -d

Keep the same data volume across upgrades. Restarts reuse existing databases and perform no first-run downloads. Run init again when adding an agency or repairing its stored topology. Scheduled refresh maintains agencies that have already been initialized.

Run — follow logs:
docker compose -f compose.yaml logs -f
Run — follow logs:
podman compose -f compose.yaml logs -f
compose.yaml passes VAPID_PUBLIC_KEY, VAPID_PRIVATE_KEY, VAPID_SUBJECT, PUSH_ENDPOINT_HOSTS, GEOIP_DB_PATH, and every FEED_* secret listed in .env.example through from your shell or a .env file beside compose.yaml — set whichever tiers you want before up. Push uses the built-in browser-service hosts unless PUSH_ENDPOINT_HOSTS adds exact custom hosts. Push remains disabled without both VAPID keys, and coarse-ip stays off without GEOIP_DB_PATH. Self-hosted storage is SQLite under DATA_DIR (bun run start needs it set). The explicit startup hook starts the alert scheduler and an independent topology timer for the next 04:00 UTC opportunity, using the same weekday assignments and seven-day TTL as the external remote job. Self-hosting needs neither Forgejo nor Cloudflare; SQLite remains local. Importing the server starts no timers. Startup does not refresh every agency or catch up missed runs; overlapping topology cycles share one in-flight run. Initial population and emergency refresh remain manual seed operations.

Stage check

  • docker images shows ghcr.io/joncrangle/schematic; container is Up.
  • podman images shows ghcr.io/joncrangle/schematic; container is Up.
  • curl http://localhost:3000 returns the app.
  • /sw.js serves no-cache; /assets/*.js serves immutable caching.

4Lock down with Cloudflare Access (optional)

Puts a login screen in front of the app so only the email addresses you allowlist get through. Access denies by default — no Block policy needed. All dashboard, nothing to paste.

4.1 Create the Zero Trust organization

  1. Dashboard → Zero Trust; pick a team name (fixes <team>.cloudflareaccess.com permanently).
  2. Select a plan — the Free plan covers a small allowlist like this (payment details required, not charged).

4.2 Add a login method

Easiest: One-time PIN — available out of the box under Zero Trust → Integrations → Identity providers.

Or Google OAuth (works with personal Gmail, no Workspace needed): Google Cloud Console → new project → APIs & Services → Credentials → consent screen (Audience: External) → Create OAuth client (Web application) with origin https://<team>.cloudflareaccess.com and redirect https://<team>.cloudflareaccess.com/cdn-cgi/access/callback → paste the Client ID + Secret into Zero Trust → Integrations → Identity providers → Google → Test.

4.3 Create the Access Application and Policy

A policy must exist before protecting the application. Configure the application and its access rules together in the Zero Trust dashboard:

  1. Navigate to Zero Trust → Access Controls (or Access) → Applications.
  2. Click Add an application → Select Self-hosted.
  3. Application Configuration:
    • Application name: e.g. Schematic
    • Application domain: Enter your Worker domain (e.g. schematic.<team>.workers.dev or your custom domain).
  4. Login Methods: Under the Login Methods section, check the identity provider established in step 4.2 (such as Google OAuth or One-time PIN).
  5. Policies: Click Add a policy:
    • Policy name: e.g. Allow My Emails
    • Action: Select Allow
    • Session duration: Select 24 hours (recommended balance) or 1 month (for persistent PWA access).
    • Configure rules: Under Include, set Selector to Emails and enter your authorized email address(es). (Do not use "Everyone" or "Login Methods" as the rule selector, which would open access to anyone).
  6. Save the application and policy.

4.4 Bypass Access for the public read paths

The edge can only cache what it can fetch without a login, so the three public read paths from §2.9 sit outside Access while everything else stays challenged. More-specific path rules win: add a second Self-hosted application covering just those paths with a Bypass policy, and leave the main application from §4.3 untouched.

  1. Zero Trust → Access → Applications → Add an application → Self-hosted.
  2. Application name: e.g. Schematic public reads. Application domain: the same hostname as §4.3, with Path entries for /api/snapshot/*, /api/departures/*, and /api/routes-catalog/*.
  3. Policies → Add a policy: Action → Bypass, include everyone the paths serve (e.g. Everyone). Save.
  4. Confirm an incognito curl to /api/snapshot/ttc returns data with no redirect to login, while / still redirects to the team login page.

Stage check

  • Incognito visit redirects to the team login page.
  • Every allowlisted account gets in; any other account sees the block page.
  • PWA installed from the home screen keeps its session; no addresses appear in git.

5Alert Feed Proxy Daemon & Cloudflare Tunnel (optional)

Use this when an upstream blocks the deployment runtime's egress, or when parsing a large supported GHD service-alert board directly in a Worker exceeds its compute budget.

5.1 Architecture

Cloudflare Workers execute from cloud edge datacenters. Certain transit authority advisory portals block requests from cloud datacenter IP addresses with HTTP 403 or bot challenges. The daemon also moves supported GHD board fetching and HTML parsing out of Workers: it polls the board on an unblocked host, turns parsed advisories into standard GTFS-Realtime Protobuf (FeedMessage), and exposes the cached feed to your Cloudflare Worker via a Cloudflare Tunnel without opening inbound firewall ports.

5.2 Running the daemon

The daemon reads its served-feed registry from the JSON file named by ALERT_FEED_CONFIG. The repository Compose service mounts services/alert-feed-daemon/feeds.json at /etc/alert-feed-daemon/feeds.json. Its default serves YRT, GRT, DRT, Milton, and OC Transpo. YRT needs the daemon because its WAF blocks Workers; the other three GHD boards use it to move their large HTML parse off Workers. The registry supports the existing ghd-news-service-advisories parser, so a compatible board can be added in JSON without a Rust change or image rebuild. The rss kind validates and forwards OC Transpo's RSS document unchanged at /oc-transpo.xml, preserving metadata for the existing decoder. RSS decoding remains in Workers. Upgrade the daemon binary/image for RSS support, then restart it after editing the mounted file.

Each entry pairs an id with an upstreamUrl, parser, routeParser, and IANA timeZone. The ID determines the public path /<id>.pb. Optional maxAgeMinutes matches the operator's publication policy (0–4,294,967,295 minutes). RSS entries instead use parser: "rss" and omit routeParser, timeZone, and maxAgeMinutes; their path is /<id>.xml. Registry defaults set pollIntervalSecs and maxStalenessSecs; the existing global environment variables override those defaults, and per-feed values override both. Poll intervals must be positive and representable by the runtime timer. A staleness threshold of zero makes a cached feed stale as soon as its recorded age becomes positive. An empty feeds array starts no pollers while keeping /health available.

Roll out the daemon first. Update the mounted registry and restart the daemon, then verify /yrt.pb, /grt.pb, /drt.pb, and /milton.pb return protobuf feeds, and /oc-transpo.xml returns RSS through the tunnel with the configured token. Configure the Worker secrets next, and only then deploy the manifests that route Cloudflare alert sources through the daemon. If FEED_ALERT_PROXY_BASE_URL is absent, those proxy sources are inactive: YRT, DRT, Milton, and OC Transpo have no alert source on Workers; GRT retains its separate official GTFS-Realtime source, but its combined snapshot stays stale because the required GHD board is missing. A daemon request or auth failure is reported as stale feed data rather than triggering direct HTML parsing in the Worker.

Registry entry for another compatible GHD board:
{
  "id": "agency",
  "enabled": true,
  "parser": "ghd-news-service-advisories",
  "upstreamUrl": "https://www.example.ca/Modules/News/en/serviceadvisories",
  "routeParser": "standard",
  "timeZone": "America/Toronto",
  "maxAgeMinutes": 10080
}

Generate a shared secret token using OpenSSL, then run the daemon either as a standalone compiled binary or as a container:

Run — generate secret token:
openssl rand -hex 32

Option A — Native binary:

Run — compile release binary:
bun run alerts:build
Run — start daemon:
PORT=3001 FEED_ALERT_PROXY_TOKEN=your_generated_token ALERT_FEED_CONFIG=/path/to/feeds.json bun run alerts:start

Option B — Containerized (Docker / Podman):

Pull and run the pre-built multi-arch image (recommended):

Run — start pre-built container:
docker run -d --name alert-feed-daemon -p 3001:3001 -e FEED_ALERT_PROXY_TOKEN=your_generated_token -e ALERT_FEED_CONFIG=/etc/alert-feed-daemon/feeds.json -v "$PWD/services/alert-feed-daemon/feeds.json:/etc/alert-feed-daemon/feeds.json:ro" ghcr.io/joncrangle/alert-feed-daemon:latest

Or start it as part of your stack via Docker Compose:

Run — start via compose:
FEED_ALERT_PROXY_TOKEN=your_generated_token docker compose -f compose.yaml up -d alert-feed-daemon

Or build the image locally from source:

Run — build image locally:
docker build -f services/alert-feed-daemon/Dockerfile -t ghcr.io/joncrangle/alert-feed-daemon:latest .

5.3 Exposing via Cloudflare Tunnel

Route an ingress hostname (e.g. alerts.yourdomain.com) through your Cloudflare Tunnel to the daemon's port (3001). Refer to the official Cloudflare Tunnel documentation for managing tunnels via the Zero Trust dashboard or CLI.

5.4 Connect the Worker to the Proxied Feed

Configure your tunnel base URL and shared token in your Cloudflare Worker secrets:

Run — deploy the proxy base URL and token to your Worker:
bunx wrangler secret put FEED_ALERT_PROXY_BASE_URL
# Enter your tunnel origin, e.g.: https://alerts.yourdomain.com

bunx wrangler secret put FEED_ALERT_PROXY_TOKEN
# Enter the same FEED_ALERT_PROXY_TOKEN used by the daemon

The YRT, GRT, DRT, Milton, and OC Transpo manifests declare baseUrlSecretName: "FEED_ALERT_PROXY_BASE_URL" on their Cloudflare-only proxy sources. Once the secret is provisioned, Schematic activates and rewrites each URL to the shared tunnel origin and its feed path:

Manifest configuration (under alerts):
{
